## 3. Mô hình quyền và migration

- `ADMIN`: truy cập khu quản trị như cơ chế hiện có, đọc C12 và danh sách/chi tiết admin/catalog. Không có quyền quản lý admin nếu thiếu permission.
- `ADMIN_MANAGER`: role bổ sung, chứa permission `administrators.manage`; phải đồng thời có ADMIN để dùng các endpoint C12. Có quyền cấp/thu hồi ADMIN, cấp/thu hồi ADMIN_MANAGER, khóa/mở tài khoản khác. Các chức năng admin cũ vẫn dùng quyền hiện có; không triển khai RBAC chi tiết cho màn khác.
- Thêm admin bằng **email của tài khoản đã đăng ký và đang hoạt động**, không tạo tài khoản/mật khẩu thay người dùng. Giữ USER/ORGANIZER và vai trò khác khi thu hồi ADMIN; xóa cả ADMIN_MANAGER khi thu hồi ADMIN.
- Mutation serialize bằng khóa row role ADMIN trong transaction; re-read trạng thái/role/permission của actor sau khóa để không dùng principal cũ. Kiểm self-change, manager cuối cùng, version SHA256 gồm timestamp đầy đủ/role/permission/status/lock; lỗi409 buộc UI tải lại.
- Sau cấp/đổi/thu hồi quyền hoặc khóa/mở: revoke toàn bộ phiên của tài khoản đích, người dùng đăng nhập lại. API resolve cũng đọc quyền từ DB mỗi request.
- Audit append và thay đổi role/status/session cùng transaction; lỗi audit rollback tất cả. API customer status được siết kiểm customer sau khóa row, tránh đi vòng cập nhật trạng thái ADMIN qua `/admin/users/:id`; không thay giao diện C2.
- Migration **AdminManagement1793812800000** chỉ thêm role/permission/mapping vào bảng Auth hiện có, không tạo bảng mới. Khi chạy lần đầu, **các ADMIN đang ACTIVE và chưa khóa được bổ sung ADMIN_MANAGER** để giữ quyền quản lý hiện hữu. Admin tạo sau đó không tự có quyền này. Script seed development được bổ sung ADMIN_MANAGER; phải migrate trước seed. Không chạy seed trên dữ liệu hiện hữu trong phiên.
- Migration đã đăng ký ở scripts/migrate và CLI config; down từ chối xóa lịch sử. Trên DB cô lập mới: migrate áp dụng đủ6 migration, lần chạy tiếp theo trả `Applied migrations: []`.

## 4. API được phát triển và xác minh trước tích hợp UI

Prefix `/api`. Môi trường HTTP kiểm thử: source API bind loopback port ngẫu nhiên và **8033**; PostgreSQL Docker `eventhub-c12-test`, loopback **55472**, các database hậu tố `_test`. Không truy cập DB ứng dụng hoặc provider thật. Cấu hình SePay/VNPay trong fixture được đánh dấu test/sandbox, không phải dữ liệu vận hành.

| Method/path | Input/contract | Quyền/kết quả kiểm |
|---|---|---|
| GET `/admin/settings/payment-information` | Không body/query; `{sepay:{configured,enabled,environment,bankCode,accountNumber,accountName,transferContent,webhookUrl},vnpay:{configured,enabled,environment,merchantCode,checkoutUrl,returnUrl,ipnUrl,name}}` | ADMIN200; guest401; USER403; no-store. Fixture SePay Test enabled, VNPay Sandbox configured nhưng disabled |
| GET `/admin/administrators/catalog` | `{roles:[{code,name,permissions:[{code,name}]}],canManage}` | ADMIN200; ADMIN thường canManage=false, manager=true; guest401/USER403 |
| GET `/admin/administrators` | q≤200, page0..10000, limit1..100 default10; `{items,pagination:{page,pageSize,total,totalPages}}` | 200, search customer không lẫn vào admin, page1/limit1 khác page0; input âm/limit101 trả400 |
| GET `/admin/administrators/:id` | UUID; DTO identity/status/locked/lockReason/roles/permissions/manager/version | 200 cho admin tồn tại,404 sau thu hồi ADMIN; không trả password/reset/session fields |

| PATCH `/admin/administrators/:id` | `{version,admin,manager,locked,reason}` strict; reason3..1000 | Manager200; stale409; self-change400; hai manager sửa nhau đồng thời chỉ1success, request còn lại401/403; audit fail500 rollback; chỉ customer endpoint không thể bypass |

Tất cả routes C12 đọc/ghi được đặt Cache-Control no-store, qua protect và ADMIN guard. Mutation re-authorize permission ở domain sau serialization. Route/controller ở app.ts gọi Auth public→administrators domain→owner-scoped persistence; payment information qua Payment public. Boundary check PASS.

HTTP500 là lỗi audit chủ động tạo trong fixture để xác minh rollback, không phải lỗi vận hành chưa sửa. Log chỉ method/path/status/code, không chứa token/password. ## 6. Kết quả cuối và giới hạn rollout

**ĐÃ TRIỂN KHAI SOURCE — ĐẠT CÓ ĐIỀU KIỆN theo scope đã chốt**, tích hợp API/frontend đã xác minh trên môi trường cô lập, không còn blocker thiếu API cho scope này. Stitch giữ nguyên.

**Chưa áp dụng migration/restart/redeploy API8000 hoặc DB ứng dụng hiện hữu.** Không thay credentials/payment mode/worker, không thực hiện giao dịch thật. API8000 cũ cần rollout backend cùng migration trước khi dùng C12 với dữ liệu hiện hữu; frontend source mới không chứng minh runtime8000 đã hỗ trợ. VNPay Sandbox trong fixture có cấu hình hợp lệ nhưng chưa kích hoạt; không kiểm thanh toán VNPay end-to-end trong phiên.

Rollout cần thực hiện trong môi trường đích theo quy trình đang có: build backend; review/applied migration AdminManagement bằng migration runner (có đủ quyền và TLS phù hợp môi trường); deploy/restart API với config hiện có; build/serve frontend; đăng nhập lại tài khoản ADMIN_MANAGER, kiểm GET thông tin cổng/catalog/list. Không chạy development seed trên DB hiện hữu. Với DB mới chưa có admin, cần provisioning admin đầu tiên có ADMIN và ADMIN_MANAGER theo cơ chế thiết lập hiện có; không mở API tự bootstrap public.

Chưa xác minh full a11y/contrast/screen reader/browser khác/pixel-diff tuyệt đối, performance benchmark và rollout production/static8000. Bộ test dùng role/perms thực tế mở rộng một role quản lý admin, không hứa phân quyền chi tiết cho các chức năng quản trị khác.
