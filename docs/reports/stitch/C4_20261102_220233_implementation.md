## 5. Thao tác đã thực hiện

### 5.1. Backend

- Mở rộng `GET /admin/organizer-applications` với schema `q` (≤200 ký tự, mặc định rỗng), `status` (enum 3 giá trị), `page` (0–10000), `limit` (1–100, mặc định 10).
- Thêm các truy vấn thuộc module `auth`:
  - `adminApplications(q, status, limit, offset)` — lọc ILIKE 5 trường + lọc trạng thái, sắp xếp mới nhất.
  - `adminApplicationsCount(q, status)` — tổng theo cùng điều kiện lọc.
  - `organizerStats()` — `total` / `active` (`APPROVED`) / `pending` (`PENDING`) trên toàn bộ bảng (không theo `q`/`status`).
- Thêm API công khai `auth.adminApplications(principal, ...)` yêu cầu role `ADMIN`, chạy 3 truy vấn song song, trả `{ rows, pagination, stats }`.
- GMV được ghép trong route bằng 3 module public API, không phá vỡ ranh giới sở hữu bảng:
  - `event.eventIdsByOrganizers(userIds)` — chỉ đọc `id, organizer_id`.
  - `order.paidRevenueByEventIds(principal, eventIds)` — có guard `ADMIN`, chỉ đọc `orders` với `status='PAID'`.
  - `organizerGmv(...)` cộng dồn theo `organizer_id`, trả `gmv` dạng string (BigInt).
- Toàn bộ route bọc trong `db.snapshot.run` để stats / danh sách / GMV nhất quán trong một snapshot.
- Giữ nguyên `POST .../:id/review` và `/me/organizer-applications` cho A5.

### 5.2. Frontend

- Tạo `client/src/pages/admin/C4ManagerOrganizer.tsx` (TSX + CSS trong **một file**, CSS trong `const styles`, viết xuống dòng).
- Nối `Admin.tsx`: `tab === "applications"` trả `<C4ManagerOrganizer />`; dùng `AdminShell` chung (sidebar + header admin), không dựng lại shell.
- Thành phần giao diện:
  - Breadcrumb + hero “Quản lý Ban Tổ Chức”, nút nhanh “Xét duyệt hồ sơ mới” kèm badge `stats.pending`.
  - 3 KPI (Tổng đối tác / Đang hoạt động / Chờ thẩm định).
  - 4 tab trạng thái kèm số lượng (Từ chối = `total − active − pending`).
  - Tìm kiếm debounce 250ms gọi API `q`; nút Làm mới.
  - Bảng 6 cột: Đơn vị · Người đại diện & liên hệ · MST/Pháp nhân · Tổng doanh thu GMV · Trạng thái · Thao tác.
  - Phân trang `1–N / Tổng`, giới hạn trang khi `page >= totalPages`.
  - Modal chi tiết đầy đủ trường hồ sơ; xét duyệt inline cho hồ sơ `PENDING`; từ chối bắt buộc lý do; đóng bằng Escape, focus vào nút đóng.
  - Loading, empty (phân biệt “không có dữ liệu” và “không khớp tìm kiếm”), error có nút thử lại, notice thành công.
  - Responsive: breakpoint 1000px và 720px; bảng cuộn ngang trong card.
- Không hiển thị/không gọi các chức năng đã loại bỏ.

## 7. API đã xác minh

Môi trường: PostgreSQL 17 tạm cô lập (`eventhub_test`, container `eventhub-c4-verify`, cổng 55432), app dựng từ `dist` với migration thật; seed 5 tài khoản, 4 hồ sơ BTC, 1 sự kiện, 1 đơn `PAID` 123.456 và 1 đơn `CANCELLED` 999. Không gọi API production/Live. Container và script kiểm thử đã được xóa sau phiên.

| # | Kiểm thử | Kết quả thực tế |
|---|---|---|
| 1 | `GET /api/admin/organizer-applications` không token | **401** |
| 2 | `GET ...?page=0&limit=2` token ADMIN | **200**; `items=2`, `total=4`, `totalPages=2`, `stats={total:4,active:1,pending:2}` |
| 3 | `GET ...?page=1&limit=2` | **200**; `page=1`, trả các hồ sơ còn lại |

| 6 | `GET ...?status=REJECTED` | **200**; trả hồ sơ đã từ chối |
| 7 | `GET ...?status=INVALID` | **400** (zod enum) |

| 9 | `POST .../:id/review` từ chối không lý do | **400** |
| 10 | `POST .../:id/review` từ chối có lý do | **200**; trạng thái `REJECTED`, `rejection_reason` lưu đúng |

Ghi chú: `GET /api/health` trên Docker `127.0.0.1:8000` trả `000`; container `pbl6-api-1` ở trạng thái `unhealthy` và log lặp “Request failed Error Connection terminated unexpectedly” (API không kết nối được DB của môi trường Docker). Vì vậy kiểm thử HTTP được thực hiện trên PostgreSQL tạm cô lập thay vì Docker hiện tại; không chỉnh sửa container/DB của người dùng.
